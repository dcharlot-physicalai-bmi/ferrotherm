# The board you measure on

A lab guide for the Kria KV260, the second of the two demo boards. [GUIDE.md](GUIDE.md) is about
the Alchitry Pt V2, where you place logic and configure the chip from Rust. This one is about the
board where you find out what that logic costs in joules.

Work through it at a terminal. Each section asks you to predict before you run.

## Start here

```sh
cargo run --release -p ferrotherm-silicon --example frame_parity -- <any-bitstream>
```

Point it at anything: an Artix-7 `.bit` from this repository, a `.bit.bin` from the board's own
`/lib/firmware`. It reads the container, works out the device family from the frame geometry, and
reports one number — how many frames carry the parity that every vendor frame carries.

```text
k26_bist_template.bit.bin
  UltraScale+   93 words/frame: 20956 frames, 16662 occupied, 0 odd, 0 words left over
  VENDOR-SHAPED: every frame carries its parity
```

Run it now on a file from each board. The rest of this guide is about why those two files are so
different and what the difference costs you.

---

## What are the two boards for?

They answer different questions, and neither answers the other's.

| | Alchitry Pt V2 | Kria KV260 |
|---|---|---|
| Part | XC7A100T, Artix-7 | ZU5EV, Zynq UltraScale+ |
| What this library does with it | Places, routes and configures it, end to end, in Rust | Reads and checks bitstreams; writes the RTL that goes on it |
| How a design gets on it | `openFPGALoader` over JTAG | The kernel's FPGA manager |
| What it tells you | That a fabric can be built from open data | What a fabric costs, in watts, on a rail you can read |

The KV260 carries an INA260 on the power rail. That is the whole reason it is in the ladder: it is
the board that answers "how many joules is one spin flip", and no amount of simulation answers it.

## Why can't this library configure the KV260 the way it configures the Pt V2?

Because the bitstream path and the fabric map are two different things, and only the first is
ported.

The bitstream side is done, and the [`usplus`](src/usplus.rs) module holds it: the frame geometry,
the frame-address fields, and the container the board loads. Three things differ from 7-series, and
each one is a way to read a valid bitstream and conclude it is empty.

**The frame is 93 words, not 101.** Measured rather than assumed: a Kria K26 reference image's
frame data is 1,948,908 words and its partial template's is 15,531. Both divide by 93 exactly.
Neither divides by 101.

**The minor field is eight bits, not seven.** Across 20,905 frame-address writes the minor runs to
255, and the block-RAM content columns are exactly 256 frames deep. Carry the 7-series `0x7F` mask
across and every wide column folds in half — silently, because every address still decodes and
every frame still writes.

**The file starts with a decoy.** What the FPGA manager loads is a boot image: little-endian
32-bit words, opening with a header that itself contains `0xAA995566` followed by the tag `XLNX`.
A reader that stops at the first sync word parses the header as configuration and finds nothing.

**Predict first:** you have a 1.9 MB file and a reader that finds the sync word at word 8. How many
configuration frames will it report? (The real stream begins at word 2,580.)

What is *not* ported is the fabric map — the UltraScale+ equivalent of the tilegrid, the switch
database and the segbits. Without it there is nothing to place into or route through.

**The lever:** that map is open data too, published by Project U-Ray in the same shape Project
X-Ray publishes the 7-series one. The geometry it would plug into already exists and is tested.
What stands between here and a KV260 configured from Rust is a database port, not a discovery.

## How do you get a design onto it, today?

Through RTL. [`ferrotherm::hdl`](../src/hdl.rs) emits synthesizable Verilog for a fabric, vendor
synthesis turns it into a `.bit.bin`, and the kernel loads it:

```sh
sudo cp design.bit.bin /lib/firmware/
echo design.bit.bin | sudo tee /sys/class/fpga_manager/fpga0/firmware
sudo dmesg | grep "writing .* to Xilinx ZynqMP FPGA Manager"
```

**Predict first:** you skip the `cp`. What does `/sys/class/fpga_manager/fpga0/state` say
afterwards?

It says `operating`, because the previous design is still operating. The write failed, the old
bitstream kept running, and the status file is telling you the truth about a question you did not
ask. The kernel log is the only place the load itself appears. Check it every time.

## How do you make a power number mean anything?

Two things must be true before the rail tells you about your design.

**The design must be reachable.** Synthesis deletes logic that cannot affect an output, and a
sampler's state is read by nothing. An unwrapped fabric optimises down to almost nothing, and the
board then correctly measures near-zero power for a design that is not there. Fold every state bit
into one registered bit, drive something with it, mark both `DONT_TOUCH`.

**The instrument must respond.** Before trusting a sensor, move it with a load you already
understand. Spinning the KV260's four processor cores shifts the rail by `+0.681 W` against a
baseline that returns to within `0.008 W`. A sensor that does not move under a load you chose will
not move under one you did not.

Then measure A, B, A — and reload the first design at the end:

| pass | fabric | watts |
|---|---|---|
| 1 | p-bit, 1,024 spins | 3.870742 |
| 2 | p-trit, 64 sites | 4.011461 |
| 3 | p-bit, 1,024 spins | 3.877865 |

The first design reproducing to 0.18% is what makes the middle row a measurement rather than a
drift. Without the third pass the two are indistinguishable.

**Predict first:** at 100 MHz with two colour classes a sweep takes two clocks. The p-bit fabric
has 1,024 spins and the p-trit fabric 64 sites. Which performs more updates per second, and by what
factor?

<details>
<summary>The answer, and what it makes a unit cost</summary>

The p-bit fabric runs `5.12e10` updates a second, the p-trit `3.2e9` — sixteen times more.
Dividing the power each adds over the common reference:

| | per update | per unit, lookup tables | registers per unit |
|---|---|---|---|
| p-bit | 7.8 pJ | 43.6 | 33.0 |
| p-trit | 168 pJ | 628 | 34.2 |

A p-trit update costs **21.5 times** a p-bit update, where the area ratio is 14.4. The extra comes
from the three random draws and the multiplexer tree, which switch on every update, while a lookup
table holding a truth table does not.

Both figures share one reference, so the *ratio* is sound. The absolutes are lower bounds: the
reference pass had a previous design loaded rather than an idle fabric.
</details>

## What does a parity check tell you about a bitstream you did not write?

That it is the shape a vendor tool produces — or that it is not.

Every configuration frame carries an error-correcting code so the device can scrub its own memory
for upsets while the design runs. This library implements the part of that code it can back with
evidence: the overall parity bit. Two independent lines of evidence fix it.

The field is reserved. Sweeping the whole Project X-Ray Artix-7 database for a configuration bit
that resolves into frame word 50, bits 0 to 13, finds none — out of 1,404 segbits in the three tile
types that occupy that word, the lowest bit index is 14. Four tile types, reverse-engineered
separately, agree on the same boundary.

And real frames obey it:

| source | frames | odd parity |
|---|---|---|
| Four Vivado designs, XC7A35T | 21,680 | 0 |
| Kria K26 reference image, ZU5EV | 20,956 | 0 |
| Kria K26 partial template, ZU5EV | 167 | 0 |

**Predict first:** this library generates its own 7-series bitstreams and a board accepts them.
How many of its 40 frames do you expect to carry the parity?

<details>
<summary>The answer</summary>

Twenty. Half, which is what "never set" looks like when the underlying counts are arbitrary. The
board raised `DONE` anyway, because configuration does not check the code — readback and upset
detection do. A structural defect that the device does not object to is exactly the kind that
survives to production, and the only thing that finds it is comparing against something you did
not write.

`FrameBuf::set_x7_parity` fixes it, and the lab reports the count as one of its stages.
</details>

**What is still open.** The other twelve bits of the field are a Hamming code whose bit-to-syndrome
map this review did not recover — raw linear position and power-of-two-skipping labellings were
tried under forward and reversed word order, forward and reversed bit order, and 66 offsets, and
none reproduced the vendor frames. They are left zero. The lever here is a readback: the device's
own `FRAME_ECC` output, captured against a frame you control, gives the syndrome directly.

## When something is wrong, what does it look like?

| What you see | What it means | The check |
|---|---|---|
| A bitstream reads as zero frames | The boot header's decoy sync word | Take the sync a no-op follows |
| Frame count is not a whole number | The other family's geometry | `Survey::remainder` |
| Half a wide column writes to the wrong place | A 7-bit minor mask on an 8-bit field | `usplus::Far`, not `tilegrid::Far` |
| Flash succeeds, behaviour unchanged | The file was not in `/lib/firmware` | `dmesg`, never `state` |
| The board measures ~0 W | The fabric was optimised away | `DONT_TOUCH` and an observable sink |
| A power delta that will not reproduce | No return pass | Measure A, B, A |
| A parity verdict on a file with no frames | Nothing was counted | `Survey::vendor_shaped` requires `frames > 0` |

## Exercises

1. **Find the decoy.** Read a `.bit.bin` as big-endian words and search for the sync word. Predict
   how many you find, then read it little-endian and count again.
2. **Break a column.** Decode a real frame address with `tilegrid::Far` instead of `usplus::Far`.
   Predict which field changes and by how much, then check against `usplus::Far::decode`.
3. **Move the instrument.** Load the processor cores and watch the rail. Predict the settling time
   before you predict the magnitude.
4. **Price a variable.** Using 43.6 lookup tables and 7.8 pJ for a p-bit against 628 and 168 pJ for
   a p-trit, work out the cheaper way to hold one three-state variable. Then read
   [`pdit`](../src/pdit.rs) on why the dearer one can still be the right choice.
